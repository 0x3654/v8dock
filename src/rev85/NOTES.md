# Реверс клиентского протокола кластера 1С 8.5 (DTSecurityChannel)

Статус: старт 06.09.2026 (вечер). Цель: понять, почему 8.5-клиент отвергает
8.5-кластер («не является адресом кластера») и, в целом, формат нового
клиент-серверного протокола. Материал: pcap /tmp/cap85.pcap (290 МБ,
дампы внутри контейнера server1c85), бинарники клиента 8.5.1.1522 на маке.

## Формат на проводе (из pcap, сессия client 192.168.65.1:49981 → ragent:2540)

1. TCP connect → сервер сразу шлёт **5 байт: `53 f5 c6 1a 7b`** ('S'+4).
   КОНСТАНТЕН между сессиями (13:12 и 13:13) → magic/версия, не nonce.
   Байт-паттерн найден в **rtrsrvc.dylib** (offset 0x602130).
2. Клиент → **20 сырых байт** (разные между сессиями → nonce/ключевой
   материал): `22 48 55 b5 ...`.
3. Дальше — фреймы: **2-байтовый префикс** (разный: `d7 00` у клиента,
   `bf 00` у сервера — тип/флаги, НЕ длина: тела по 184 Б) + **UTF-8 BOM**
   + JSON-строки, разделённые CRLF:
   - клиент: BOM + `"n",` + CRLF + `{#base64:<чанки по \r\r\n>}`
   - сервер: BOM + `{#base64:<чанки>}`
4. base64-склейка чанков → 118–123 Б бинарного payload'а, высокая
   энтропия → **шифрование**; protobuf-разбор спотыкается на 2-м байте
   (varint-длина невалидна) → зашифровано целиком.
5. В сессии с бОльшим обменом (другой порт) был клиентский пакет 699 Б и
   серверный 381 Б — тот же envelope, больше данных.

## Что НЕ вскрылось

XOR-деривации от nonce/greeting/sha1/md5 — читаемость шумовая (~0.35).
Канал шифруется настоящим шифром, ключ видимо выводится из 20-байтового
клиентского материала (и, возможно, серверного вклада внутри первых
фреймов).

## Карта реализации (клиент 8.5.1.1522, macOS, /opt/1cv8/8.5.1.1522/)

- **rtrsrvc.dylib** — транспорт: `DTSecurityChannel` (CLSID_DTSecurityChannel,
  IDTSecurityChannel), `DataTransferFactoryClient`; boost::asio. Здесь живёт
  magic `53f5c61a7b`. Именно этот модуль фигурирует в ошибке клиента:
  `line=1068 file=src/rtrsrvc/src/DataExchangeTcpClientImpl.cpp`.
- **backend.dylib / backbas.dylib / ext.dylib / frntend.dylib / inet.dylib**
  — GOST-стек: CryptoPro, GOST89/Gost28147 (Магма), GOST2001/2012 (подпись),
  **grasshopper/kuznyechik** (Кузнечик). Крипто-примитивы канала — тут.
- **core85.dylib** — `#base64` в UTF-16 → JSON-envelope парсится в core85.
- `{#base64:` как текст найден и в *.res (ресурсы локализации — вероятно,
  строки формата/ошибок).

## Гипотезы

- KEX/шифр — ГОСТ: Кузнечик (GOST R 34.12-2015) + VKO-соглашение ключей;
  20 Б клиента — возможно, импорт-обёртка ключа или nonce KDF.
- Ошибка клиента «не является адресом кластера» возникает при разборе
  ОТВЕТА ragent (по tcpdump клиент кладёт трубку сразу после 381-Б ответа,
  до 2541 даже не доходит): либо расшифровка/парсинг падает, либо в ответе
  адрес, который клиент не принимает.

## Следующие шаги

1. Дизассемблировать `DTSecurityChannel::Handshake*` в rtrsrvc.dylib
   (Ghidra/IDA; arm64 macOS) — последовательность: magic → nonce → KDF.
2. Найти в backend.dylib вызовы Кузнечика от rtrsrvc (импорты/таблицы).
3. Свежий чистый pcap одного коннекта (tcpdump уже в контейнере ставить
   умеем) + повторяемость greeting при перезапуске ragent (константа
   протокола или серверный seed?).
4. Сверить с v8platform/protos (RAS API v8.service.Admin.*) — вдруг
   фрейминг родственен.
5. Прозондировать поведение: коннект «мусорным» клиентом (отправить
   magic+случайные 20 Б) — что ответит ragent (формат ошибок).
